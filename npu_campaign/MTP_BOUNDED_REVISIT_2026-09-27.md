## Decision and next gate

For this exact model/binary/policy/prompt, real MTP has demonstrated 64-token target-logit equality against two matching plain runs and an independent MTP repeat. The one differing plain run shows an intermittent **plain-path** numerical failure before its selected-token split. Therefore, a plain/MTP mismatch on this policy cannot be attributed to speculative verification without first controlling that baseline; nor does equality on this one prompt establish global MTP correctness. This reproduces the earlier pattern under the later D2D baseline rather than proving that the older EFC observations transferred unchanged.

Stop the bounded MTP revisit here. The next correctness investment is an allocation-preserving first-divergence probe for the plain step-10 logit variation, with a same-run/identical-layout plain repeat gate. Existing tensor-retention probes alter graph lifetime and can suppress the failure, so any new probe must show that the uninstrumented plain failure still occurs. Only then extend matched plain/MTP target gates to 128 tokens and multiple prompts, separately audit draft logits plus KV/recurrent accepted/rejected-prefix rollback, and finally measure untraced paired speed. Do not enable fused MTP verify or KV-only catch-up based on this result.

## Deeper continuation: plain failure survives fixed graph descriptions

The user resumed work after the bounded checkpoint. On the same D2D baseline, a second plain64 pair with fusion and replay both off differed already at the prompt logit row (NMSE `0.00880110055`, max `0.750018716`) and first selected token step 19. This shows neither fusion nor replay is necessary for a plain-path discrepancy, but changing both policies also changes the graph and trajectory; it does not isolate a root cause.

Another plain64 pair with `GGML_HEXAGON_VERBOSE=1` kept fusion/replay on and retained no tensors. Its first bit difference moved to step 31 and its first selected-token split to step 61, so logging did **not** suppress the failure. The two logs have exactly the same 7,604 `execute-op` descriptions and 3,922 `add-tensor` descriptors after normalizing process-specific absolute addresses; all logged tensor names, buffer IDs, offsets, sizes, flags and shapes match. Graph replay op counts also match. The mismatch is therefore not explained by a *visible* op sequence or tensor-layout change. This does not rule out cache state, unlogged descriptor content, async timing, or an arithmetic race. Logs: `mtp-deep-plain-fr0-{a,b}64` and `mtp-deep-verbose-{a,b}64`.

### Draft trace correction

The MTP draft context writes top-10 candidate rows to the logit trace. Its `logits-trace-selected` event records the return value of `common_sampler_sample`, but `common_speculative_impl_draft_mtp::draft()` ignores that return and instead drafts `common_sampler_get_candidates(smpl, true)->data[0].id`, the highest-probability candidate after sorting. The selected trace can therefore differ between runs even when the draft actually used and the candidate/logit row are identical. A naive application of the target comparator to draft context reported a false selected-token divergence at draft row 6 for `Hello` and row 4 for prose, although the candidate lists and logits were bit-identical. Source: `common/speculative.cpp` MTP constructor and `draft()`; `common/sampling.cpp` sampling and `get_candidates()`.

`compare_logits_traces.py --context-index 1 --draft-greedy --require-identical` now checks the draft candidate IDs, their logit bits, and the top candidate while deliberately ignoring that unused sampled-ID event. It passes all 74 draft rows across the `Hello` 128 MTP pair and all 68 across the prose 128 pair; it also passes the 36-row original D2D MTP64 repeat. This is an exact *draft-candidate trace* repeat gate, not a direct capture of every hidden/KV state cell or a proof that all draft arithmetic is deterministic on other prompts.

Next: distinguish the whole-cache call's flush/invalidate, implicit synchronization, and dirty-tracker reset effects with narrower OFF-default signed interventions, each requiring the same full target/draft gates. Reproduce the failure on the matching untreated baseline before calling any narrow arm a rescue. Do not adopt the all-cache diagnostic as a speed path.

## Fresh-build dirty-tracker factorial

The archived E956 cache-control binary was independently rebuilt from current source in isolated CMake directories. Both fresh arms use the same OFF-default whole-cache `QURT_MEM_CACHE_FLUSH_INVALIDATE_ALL` call immediately before source tensor flushing. The sole compile-time distinction is whether `octx->ctx->dirty_ranges` is cleared after that call (`reset-control`) or retained (`keep-tracker`). Both were signed, catalog membership checked, run with the same frozen host/model/policy, and the installed D2D/5CB7 baseline restored and hash-checked after each session. Local signed archives are `backup-mtp-cache-{reset-control,keep-tracker}`. Their exact DSP hashes are `8CE16D35BB1A8CE691BFBD6748DB809BB61E2BE102116511D22366CD35D6DD04` and `443B5B49D7576693245827D3BD315CF487B2303E4EBD460646A9E040CBF5591C`, respectively. They are not production candidates.

The fresh reset-control Hello64 four-arm session passed every 64-row target bit/selected-token gate and matched the archived E956 plain Hello64 trace bit-for-bit. The fresh keep-tracker control passed the same Hello64 gates and matched fresh reset-control plain bits. It then passed two independent 128-token four-arm sessions:

| Keep-tracker prompt | Plain repeat | MTP repeat | Plain vs MTP | Draft-candidate repeat | Accepted drafts |
| --- | --- | --- | --- | --- | --- |
| `Hello` | 128/128 target rows bit-identical | 128/128 | 128/128 | 74/74 candidate rows bit-identical | 52/74 both runs |
| Sky-color prose prompt above | 128/128 | 128/128 | 128/128 | 68/68 | 59/68 both runs |

Both keep-tracker plain128 traces also match their archived reset-tracker E956 plain128 counterparts bit-for-bit. The target comparator additionally checked every selected token; the draft comparator checks candidate IDs, logit bits and actual greedy top candidate, not the unused sampler-selected trace event. These results rule out dirty-tracker clearing as a *necessary* part of this particular cache-control rescue on two prompts, while leaving the cache operation's flush, invalidation, implicit synchronization, and timing confounded. Keep-tracker traced decode was about 15.5–17.5 tok/s, diagnostic only. Raw captures use `mtp-deep-keeptracker128-*` and `mtp-deep-keeptracker-prose128-*` prefixes.

A further fresh OFF-default `GGML_HEXAGON_PER_OP_WHOLECACHE_FLUSH_ONLY_REFERENCE` control replaces only `QURT_MEM_CACHE_FLUSH_INVALIDATE_ALL` with `QURT_MEM_CACHE_FLUSH_ALL`, retaining the tracker. The local SDK's `qurt_memory.h` documents that `qurt_mem_cache_clean` performs `syncht` for cache operations on Hexagon v60+, so even a flush-only success would not isolate synchronization. Qualification requires matched full-logit repeat gates, not text agreement.

The signed flush-only candidate DSP SHA256 was `3040B10D48740833359B00BD762C234420787C6D5CF7F0BA379B04AD091BF34F` (catalog `3C916C976072B5F1F39BB0E27918673282C936B1371E922F75EA5E46828CA74B`). Its Hello64 four-arm session **failed**: the two plain runs first differed in target-logit bits at step 3, then in selected token at step 55; plain A differed from MTP A in bits at step 3 and selected token at step 15. MTP A/B still matched all 64 target rows and their 36 draft-candidate rows. Plain A differed from archived flush+invalidate control at bit step 3/token step 15. Thus whole-cache *flush without invalidation* does not reproduce the earlier rescue, despite running the same cache API and keeping the tracker. It was substantially faster in this traced diagnostic (plain `26.50/26.66`, MTP `23.86/23.53` tok/s), but it is **incorrect**, so these speeds are not candidates for promotion. Raw captures: `mtp-deep-flushonly64-*`; baseline restoration printed and was verified. This makes invalidation and/or its timing side effects the next discriminant, not the tracker reset.

### Narrow source-range clean+invalidate lead

An OFF-default `GGML_HEXAGON_PER_OP_ACTIVATION_SOURCE_CACHE_REFERENCE` arm calls `qurt_mem_cache_clean(..., QURT_MEM_CACHE_FLUSH_INVALIDATE, QURT_MEM_DCACHE)` for each present, nonempty, non-weight, non-fence *source* tensor immediately before the existing dirty-tracker source flush. It does not flush the whole cache, clear the tracker, or change the op graph. The signed DSP SHA256 is `64C095F085592FA6D30EE7E9A562549FEAF1ECD6997BD09AE065DC285C617993` (catalog `4404E0B0BEEBEFFB956164FE0151017C9A01F6FC0F57ABEA6DCE279A5E3949B3`).

Its first Hello64 four-arm test passed all 64 full target-logit bit and selected-token rows for plain A/B, MTP A/B, and plain A/MTP A; the two MTP runs matched all 36 draft candidate/logit rows and accepted 27/36 drafts. The activation-source plain A trace also matched the archived whole-cache plain A trace bit-for-bit. Traced decode was plain `24.80/24.78`, MTP `22.28/22.40` tok/s—closer to the ~27/~24 tok/s baseline than the all-cache control, but not yet a rigorous speed or production qualification. Two-prompt 128-token and untreated failure-frequency gates are still needed. This narrows the candidate mechanism toward missing source-range cache maintenance; it does **not** prove the source dirty tracker is the root cause, since added cache API synchronization/timing can also matter.

The 128-token extension subsequently **passed on both prompts**. For `Hello`, plain A/B, MTP A/B and plain A/MTP A each matched all 128 complete target-logit bit rows and selected IDs; MTP A/B matched all 74 draft candidate rows and accepted 52/74. The plain A trace matched the archived whole-cache Hello128 trace bit-for-bit. Traced rates were plain `25.42/24.77`, MTP `21.92/22.02` tok/s. For the sky-color prose prompt the same three target comparisons each matched all 128 rows and selected IDs; MTP A/B matched 68/68 draft candidate rows and accepted 59/68. Its plain A trace likewise matched archived whole-cache prose128 bit-for-bit. Traced rates were plain `25.11/24.84`, MTP `24.24/23.71` tok/s. Raw captures are `mtp-deep-actsrc128-*` and `mtp-deep-actsrc-prose128-*`. Every four-arm wrapper restored and hash-checked the installed D2D DSP/5CB7 catalog.

This is a *strong reproducible diagnostic lead* for this exact host/model/policy, not a production change. The source-range arm invokes a costly synchronized cache API for every source even if it is already clean; the exact missing range, operation, and ownership transition remain unknown. Before adopting a fix, establish a same-source OFF-control failure frequency, test a third trajectory and relevant policy variations, capture untraced speed, and isolate which source ranges actually need maintenance without changing graph lifetime.
